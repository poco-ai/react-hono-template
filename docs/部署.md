# 部署

API 和 Web 都部署到 Cloudflare Workers。推到 `main` 且路径命中时，GitHub Actions 会自动部署。仓库密钥需要 `CLOUDFLARE_API_TOKEN` 和 `CLOUDFLARE_ACCOUNT_ID`。

两条部署 workflow 都先跑可复用的 `quality`（安装依赖、Biome 检查、类型检查、构建、测试），通过后才部署。Pull request 也会跑这套检查。手动 `configure-ai.yml` 还会检查 `SILICONFLOW_API_KEY` 仓库密钥，然后迁移远端 D1、写入 Worker 密钥并部署；它与常规 API 部署共用并发组，不会同时改同一个 Worker。GitHub Actions 只保留一个等待中的运行，不保证逐个发布。Bun 版本读根目录 `package.json`。

手动部署 API：进入 `apps/api` 后执行 `bun run deploy`。手动部署 Web：先在 `apps/web` 执行 `VITE_API_URL=https://api.example.com bun run build`，再执行 `bun run deploy`。部署 Web 不会自动重建静态产物。当前示例：

- Web <https://react-hono-web.poco-ai.workers.dev>
- API <https://react-hono-api.poco-ai.workers.dev>

从模板新建项目时，在第一次推送 `main` 前更换两个 `wrangler.jsonc` 的 Worker 名称、D1/KV 资源、队列和存储配置，替换 Web workflow 的 `VITE_API_URL` 以及 API 的公开 URL 配置。按实际域名设置 `TRUSTED_ORIGINS`、`APP_WEB_URL`、`BETTER_AUTH_URL`、`PUBLIC_API_URL` 和启用的 MCP 相关 URL；不用的 AI/MCP 功能可关闭。

## 第一次上线

1. 创建 D1，把实际的 `database_name` 和 `database_id` 写进 `apps/api/wrangler.jsonc`；保留绑定名 `DB`，迁移脚本按绑定查找数据库。创建 KV：`wrangler kv namespace create react-hono-kv --binding KV --update-config`。在 `apps/api` 执行 `bun run db:migrate:remote`。
2. 写入密钥（至少 `BETTER_AUTH_SECRET`）。按需配置 GitHub / Google、S3、Stripe。生产环境的 `BETTER_AUTH_URL` 用 API 源站；`TRUSTED_ORIGINS` 填自己的 Web 源站。详见[环境变量](环境变量.md)。
3. 创建主队列和死信队列，再部署带消费者的 Worker：`wrangler queues create react-hono-webhooks`、`wrangler queues create react-hono-webhooks-dlq`。`wrangler.jsonc` 的 consumer 绑定 `dead_letter_queue`，队列不存在时部署会失败。
4. Stripe：建一个订阅价格，配齐三个密钥，Webhook 指到 `<api-url>/api/stripe/webhook`。事件见 [环境变量](环境变量.md)。

`db:migrate:remote` 使用 Wrangler 的登录状态或 Cloudflare API Token；`apps/api/.env` 里的 `CLOUDFLARE_D1_TOKEN` 等变量是 drizzle-kit 的直连配置，不是 Wrangler 登录凭证。不要用 `db:push` 代替迁移，它会跳过全文搜索触发器的恢复步骤。

## 发布前

常规自动部署不会跑数据库迁移。API 有 schema 变更时，先应用对旧 Worker 兼容的迁移，再发布新代码。删除、重命名或收紧约束等不兼容变更拆成两次发布：先添加新结构并迁移读写，确认旧版本不再访问后，再清理旧结构。

```sh
cd apps/api
bun run db:migrate:remote
```

确认全文搜索的六个触发器还在。D1 重建 `issues` 或 `comments` 时会静默丢掉触发器，搜索就会返回过期或空的结果：

```sh
bunx wrangler d1 execute DB --remote --command \
  "select name from sqlite_master where type='trigger' and name like '%_search_a%' order by name"
```

应看到 `comment_search_ad`、`comment_search_ai`、`comment_search_au`、`issue_search_ad`、`issue_search_ai`、`issue_search_au`。

这次迁移如果重建过这两张表，把触发器和索引装回去：

```sh
bunx wrangler d1 execute DB --remote --file=drizzle/fts/search_fts.sql
```

`apps/api/tests/search*.test.ts` 会在本地检查同样的六个触发器，部署前跑一遍 `bun run test`。然后再推 `main`，等 `quality` 通过。
