# 架构审查

## 结论

保留当前的模块化单体，不拆服务，也不再加一层通用仓储或插件框架。真正可复用的部分是组织鉴权、应用与平台适配层的分界、共享输入契约、前端数据入口，以及一套业务能力接入多个入口的方式。Issue、看板、周期和活动流是用来演示这些边界的业务，不是扩展新应用的必经路径。

当前主要成本来自两处：**同时维护两套运行时的数据库和队列语义**，以及**一个业务变更可能影响内部 API、公开 API、缓存和工具调用**。解决方式不是把代码拆得更碎，而是让差异停在适配层、让共享规则只实现一次，并用集成测试锁住实际行为。

## 已修复

| 范围 | 问题与修复 |
| --- | --- |
| 数据库兼容 | DAO 使用 PostgreSQL 构造器没有的 D1 `.get()` / `.all()`。统一使用两边都支持的查询写法，修正配额回填、搜索中的保留字、布尔比较、时间计算、聚合结果类型和评论反应并发写入。CI 加入 PostgreSQL 和 Redis 容器，从空库开始跑迁移和业务冒烟。 |
| 调度和队列 | 冻结组织与归档项目的周期任务曾占满到期批次，活跃任务一直排不到。现在先过滤再取批次。Redis 消费循环不再并发启动同一个进程的多个批次，退出时等待当前投递结束。 |
| 自建与发布 | 分开对象存储内网地址和浏览器签名地址；修复 RustFS 镜像启动、初始化失败不报错和直传 CORS。D1 迁移改用绑定名，便于从模板改名；常规 API 部署与 AI 配置发布不会同时修改同一个 Worker。 |
| Web 数据与路由 | 项目切换、翻页或筛选时不再沿用不相关的旧行；搜索页大小参与缓存键；列表与看板共用筛选；路由资源身份变化时重置页面的局部状态。会话查询也区分未登录和服务暂时失败，不再把服务错误缓存为匿名会话。 |
| AI 与 MCP | AI 写工具在执行时消费服务端的一次性许可；审批记录来自服务端流事件；流建立失败会释放配额预留。MCP 用同一个组织判定写工具的角色和冻结状态，且未知 OAuth scope 不会得到 API key 的默认范围。 |
| CSV | 导出转义不再因长串前导引号递归溢出，保留原有导入和导出语义。 |

## 后续优先级

1. **P1 · 明确 Webhook 投递保证。** [Redis 适配器](../apps/api/src/lib/redis/webhook-queue.ts) 的 ready、processing 和 delayed 状态迁移仍是多条独立命令，进程中途退出可能丢失任务。多副本生产部署前，应做原子认领、确认和重试，或采用有租约和待确认队列的成熟实现；用真实 Redis 测试进程退出与重复交付。若业务要求「写成功就最终通知」，还需把待发送记录与业务写入放在一个事务内，而不是只改消费端。
2. **P1 · 双运行时要用真实服务约束。** CI 冒烟不是完整等价证明。[数据库类型](../apps/api/src/db/types.ts) 仍以 D1 类型描述共享 DAO，导致 TS 允许使用 PostgreSQL 不支持的方法。先扩大真实 PostgreSQL 测试覆盖面，尤其是复杂条件更新、配额事务和搜索；若需要进一步收窄类型，应从已有 DAO 的共同调用面出发，不要为了消除一个断言重造 Drizzle。
3. **P1 · 对必须强一致的库存和限额做单独设计。** Better Auth 的席位、组织数等仍有「读数量再写」的流程；串行化单次 SQL 不等于两个请求的检查与写入是原子的。仅对必须守住的额度引入原子预留或数据库约束，其余配额保持现有的轻量实现。
4. **P2 · 让 AI 历史和 MCP 权限更少依赖入口。** 优先根据服务端持久化记录恢复对话上下文，并将工具发现与执行复用同一份权限判定。工具列表是提示，不是授权，执行时仍应检查当前组织、角色和写策略。
5. **P2 · 提高克隆后的独立性。** 目前 demo 和模板共用仓库里的生产资源配置。可以先把上下游地址、资源 ID 和启用的产品能力收进一份部署清单，再考虑拆分「演示部署」与「新项目默认部署」。有真实演进需求时，按业务能力分组注册 [API 依赖](../apps/api/src/dependencies.ts)；不为追求目录对称提前抽象。
6. **P2 · 加一条跨层浏览器冒烟。** 可只覆盖登录、切换组织或项目、创建和编辑一条记录、上传附件。现有 Query/路由回归测试应保留，浏览器测试补真实会话、导航与预签名链路，不需要复制整套单元测试。
7. **P2 · 对首屏设置可测量的体积预算。** 本次生产构建的入口 JS 约 951 kB（gzip 约 278 kB），Scalar API 文档路由单块约 1.63 MB（gzip 约 487 kB）。先用构建分析确认入口里有哪些演示专用依赖，再把非首屏且低频的功能移出入口；不要通过提高 Vite 告警阈值来掩盖体积。

扩展顺序和入口见[架构](架构.md)；上线前的操作见[部署](部署.md)和[自建部署](自建部署.md)。
