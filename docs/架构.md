# 架构

Bun + Turborepo monorepo。Web 和 API 都跑在 Cloudflare 上：API 是 Worker 脚本，Web 是带 SPA 回退的静态资源。

```text
apps/api
  src/app.ts             组装 Hono 应用，供 Worker 和 Bun 入口共用
  src/platform           将运行时配置与基础设施接入应用
  src/dependencies.ts    组装 DAO 和 service；业务层不直接读环境变量
  src/routes.ts          组装路由，导出 AppType（前端类型客户端依赖它）
  src/controllers        HTTP，校验后调 service，包成统一响应
  src/services           业务逻辑。领域错误抛 ApiError
  src/dao                唯一允许写 SQL / Drizzle 的一层
  src/dto                请求和响应类型
  src/v1                 公开 API，Bearer API Key，挂在 /api/v1
  drizzle                迁移。全文搜索的可重放脚本在 drizzle/fts/

apps/web
  src/routes             TanStack Router 文件路由，守卫在 beforeLoad
  src/pages              页面
  src/features/<领域>    data.ts 管请求和缓存，components/ 管界面
  src/i18n               en.ts 是文案源，zh.ts 跟它的类型对齐

packages/shared          Zod schema、套餐限额、错误码、统一响应包
packages/ui              shadcn/ui。添加组件：bunx shadcn@latest add <name> -c apps/web
```

`@workspace/shared` 和 `@workspace/ui` 直接导出 TypeScript 源码，改完即生效。

## API

业务请求按 `controller → service → dao → db` 流动。HTTP 校验和响应交给路由与 controller；组织归属之外的业务约束（状态转换、配额、关联记录是否合法）留在 service，让不同入口复用。不要为了追求对称给每张表再加一层通用仓储，也不要让各个入口分别实现一遍写操作。

业务路由在 `/api/orgs/:orgId/*` 下，先过登录，再过组织成员。非成员 404。组织被冻结时，写操作返回 403，读和账单仍可用。owner / admin 才有的写操作走角色校验。

公开 API 复用同一套 dao / service，但在类型客户端的 `AppType` 之外。Cloudflare 上的限流用 Workers Rate Limiting，`wrangler.jsonc` 里的限额要和 `packages/shared` 的 `PLANS` 保持一致。自建进程用 Redis 按同一份 `PLANS` 做固定窗口。

## 两条入口

Cloudflare 仍是默认部署。`apps/api/src/index.ts` 导出 `fetch` / `queue` / `scheduled`，用 D1、KV、队列和定时触发器。

同一套 Hono 应用也可以跑在 Bun 进程里。`apps/api/src/server.ts` 先选定 PostgreSQL 方言，再加载 `createApp`。平台适配层先准备数据库、缓存、对象存储、Webhook 队列、限流和 CORS 来源，再交给应用。应用本身不读 Worker 绑定，也不读 `process.env`。两条入口共用业务逻辑，但各自的缓存、限流和队列不保证完全相同的投递、时序或一致性语义。

自建依赖是 PostgreSQL、Redis，以及已经接好的 S3 兼容存储（rustfs 或 MinIO）。MySQL 只留了方言名字，打开时会直接报错。表定义来自同一个 `defineSchema` 工厂；SQLite 迁移仍在 `drizzle/`，PostgreSQL 迁移在 `drizzle-pg/`。搜索在 SQLite 上继续用 FTS5 和 bm25，在 PostgreSQL 上用 `pg_trgm`，排序按更新时间。

步骤和变量见 [自建部署.md](./自建部署.md)。Cloudflare 的部署步骤不变。

同一个进程只运行一种数据库方言：schema 在模块加载时选定，不能按请求切换。需要跨表原子写入时，用 `db/run-batch.ts`，并在回调提供的句柄上创建每条语句；D1 执行批处理，PostgreSQL 执行事务。D1 批处理中的关联查询还需要为同名列设置别名。

## Web

`features/<领域>/data.ts` 是该领域唯一的数据入口：query key、请求、mutation、缓存失效放在一起。页面负责表单、弹层、跳转和文案。界面文案走 `useTranslation()`，不要写死在组件里。

列表筛选放在 URL search params 里，用 Zod 校验。`/` 对未登录用户是落地页，登录后进入第一个组织。

前端通过 `hc<AppType>` 拿到 API 的类型。客户端不会在运行时打包 Worker 代码，但 API 的路由类型变化会影响 Web 构建。开发时 `VITE_API_URL` 为空，请求走 Vite 的 `/api/` 代理；跨域部署在构建时传入 `VITE_API_URL`，同源反代则不需要。

## 克隆后怎么接入新业务

保留登录、组织成员与角色、平台适配层和 UI 基础组件；把 Issue、看板和周期任务当作演示业务，而不是所有应用都必须保留的核心。例如做一个组织内的客户目录，可以先完成一条最小链路：

1. 在 `packages/shared/src/schemas/` 定义输入，在 `apps/api/src/db/define-schema.ts` 定义数据及组织外键；如果保留两种部署方式，就为两种数据库生成迁移。
2. 在 `apps/api` 接通 DAO、service、controller 和组织子路由，再注册到 `src/routes.ts`。不要从客户端请求体推导租户身份；查询、更新和删除都用授权后得到的组织 ID 约束数据。
3. 在 `apps/web/src/features/<领域>/data.ts` 集中定义请求、query key、mutation 和缓存刷新；页面只负责表单、筛选、导航和反馈。组织查询键以 `["orgs", orgId, …]` 开头。
4. 先测试正常路径、组织隔离、角色限制及写入后读缓存的表现。需要开放 API、Webhook 或 AI/MCP 时再接对应入口，不必为每张业务表都做一遍集成。AI 与 MCP 复用 `capabilities/` 中明确声明输入、权限和副作用的能力，不直接访问 DAO。

替换演示模块时，先解除路由、导航和对外能力的引用，再移除组件和服务；已部署的数据库用新迁移退役旧表，不要改历史迁移。从模板衍生的产品只需要一条部署路径时，明确选择并维护它，比保留没验证过的双运行时更简单。

更细的约定（缓存失效、FTS 触发器、Workers 限制）在 [AGENTS.md](../AGENTS.md)。
