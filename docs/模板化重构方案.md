## 1. 背景与目标

### 1.1 问题陈述

本仓库是一个功能完整的 multi-tenant issue tracker 模板（mini Linear），长期目标是让使用者按需取用：

- **Preset 变体**：`minimal` / `ai` / `full` 等预定义组合；
- **按特性定制**：通过脚手架勾选特性（webhooks、billing、AI、MCP……）生成定制项目。

当前结构"作为产品"是清晰的（严格分层、单一组合根、feature-data 约定），但"作为模板"存在六个结构性障碍：

| # | 障碍 | 证据 |
|---|------|------|
| 1 | **一个特性散落 ~10 个目录** | AI 分布在 `ai/`、`mcp/`、`capabilities/`、`services/ai-*.service.ts`（5 个）、`dao/ai-*.dao.ts`（5 个）、`routes/ai.ts`、`db/define-schema.ts`、`routes.ts`、`dependencies.ts`、`scheduled.ts` |
| 2 | **core 反向依赖可选特性** | `quota.service` 注入 `aiUsageDao`（settle 内记录 AI 用量）；`cleanup.service` 注入 `aiConversationDao`；`planService` 注入 9 个 service；`issueService` 直接注入 `webhookDeliveryService` / `notificationService` |
| 3 | **DB schema 与迁移是单体** | `define-schema.ts` 1758 行、51 张表；26 个线性迁移目录无法按特性挑选；FTS 触发器与核心表交织 |
| 4 | **基础设施配置硬编码** | `wrangler.jsonc` 写死 `database_id`、KV id、queue 名、4 个 rate limiter namespace（2 个 AI 专属）、生产 URL |
| 5 | **Web 三个单体** | `en.ts` 2005 行 / `zh.ts` 1905 行混装全部文案；`ChatProvider` 挂在 `org-layout.tsx` 全局壳；landing 营销全量功能 |
| 6 | **无特性注册表** | 组合靠 `dependencies.ts`（457 行）+ `routes.ts` 的命令式代码；`packages/shared` 也是全量知识（`plans.ts` 含 AI 配额） |

### 1.2 有利条件（已核实）

改造不是从零开始，现有代码已经埋好了正确的种子：

- **手写 DI 工厂**：`createXxxDao(db)` / `createXxxService()` 全覆盖，天然支持按需装配；
- **可选注入已是惯例**：`cleanup.service` 的 `conversationDao?`、`quota.service` 的 `usageDao?: Pick<AiUsageDao, "record">`、`audit?` 都是可选参数——port + 默认实现的模式与代码风格同构；
- **capabilities 已是注册表形状**：`createCapabilityRegistry(deps): CapabilityEntry[]`，AI SDK 与 MCP 只是两个适配面；
- **Web 导航已数据驱动**：`ORG_SIDEBAR_NAV`（带 `when` 谓词）、`PALETTE_ACTIONS`（带 `when`）都是数组渲染，缺的只是"谁拥有这些数组"；
- **i18n 顶级 key 已按领域对齐**：`en.ts` 58 个顶级 key（`ai:`、`mcp:`、`issues:`、`comments:`……），拆分是机械操作；
- **`platform/` 已抽象部署目标**：cloudflare / self-host 是第一个轴，preset 是第二个轴；
- **运行时降级先例已存在**：`AI_ENABLED`、`MCP_ENABLED`、`BILLING_MOCK_MODE`。

### 1.3 目标

1. 任一特性可从代码库中**整体移除**，移除后剩余代码类型检查、构建、测试全部通过；
2. `minimal` / `collaboration` / `planning` / `saas` / `ai` / `full` 等 preset 由声明式清单定义，一键生成；
3. 生成的项目是**干净的所有权转移**（用户拿到不含未启用特性代码的仓库）；
4. 模板仓库自身永远保持 `full` 形态，现有质量门（check / typecheck / build / test）在**每个 Phase 结束时都必须全绿**——不允许长期分支；
5. 每个 preset 的生成物在 CI 中持续验证（模板可信度的生命线）。

### 1.4 非目标

- **不做运行时动态装卸特性**（保留 `AI_ENABLED` 这类门禁，但不新增）；
- **不承诺生成项目的无缝升级**——生成后即为用户代码，升级靠 diff（文档需明示）；
- 不重写业务逻辑、不更换技术栈、不调整 drizzle-orm/better-auth 版本策略；
- 不在本方案内做 monorepo 工具迁移（保持 bun + turbo）。

## 2. 总体方案

### 2.1 关键决策：编译期裁剪为主，运行时降级为辅

| | A. 编译期裁剪（本方案主体） | B. 运行时开关（辅助） |
|---|---|---|
| 形态 | 脚手架按 preset 生成代码 | 全量部署，env/org 门禁 |
| 优点 | 用户只见所启功能；认知负担 / 包体积 / 攻击面最小 | 实现便宜 |
| 缺点 | 实现成本高；用户升级难 | 代码仍在，只是不可见 |
| 定位 | **模板的本职** | 保留给 AI（`AI_ENABLED`）、billing mock |

业界先例：create-next-app 的 flags、Better-T-Stack、shadcn registry（代码所有权转移模型）。

### 2.2 核心概念

```
Feature        一个可整体启停的业务能力单元（issues、billing、ai……）
               = API 切片 + Web 切片 + shared 切片 + schema 表组 + env 契约 + 文档

Feature Module 特性的注册协议实现（api: ApiFeatureModule / web: WebFeatureModule）
               声明依赖、贡献 services/daos/路由/能力/清理钩子/导航/文案……

Feature Manifest 特性清单（声明式 JSON），声明启用的 feature 集合与平台目标

Preset         预置的 manifest（minimal / ai / full ……），脚手架的入口参数
```

装配模型：`composeModules(manifest)` 把启用特性的贡献**折叠（fold）**成四个产物——`dependencies`（服务图）、`app`（Hono 应用）、`scheduledJobs`、`queueConsumers`。现有的 `dependencies.ts` / `routes.ts` / `app.ts` 退化为薄薄的折叠器。

### 2.3 特性分层与依赖图

特性分五层，**依赖只能从高层指向低层**（Tier 数字大 → 小），同层禁止互相依赖：

| Tier | 特性 | 内容 |
|------|------|------|
| 0 core | `core` | auth（better-auth、org、member、invitation、auth-policy、bootstrap、config、audit）、platform、response/validation、kv cache、db 基础设施、middleware、admin（用户/组织管理） |
| 1 workspace | `projects` `issues` `labels` `statuses` `comments` `activities` | 最小可用 issue tracker |
| 2 collaboration | `attachments`(含 media) `webhooks` `notifications`(含 issue-subscriptions) `search` `favorites` `relations` `project-updates` | 外部依赖引入者：S3、Queues、FTS5 |
| 2 planning | `cycles` `roadmap` `recurrences` `views` `templates`(issue-templates) | 计划类增强 |
| 3 commercial | `billing` `api-keys` `public-api`(v1) | Stripe、计费配额、开放 API |
| 4 intelligence | `capabilities` `ai` `mcp` | 能力层 + 两个消费面 |

依赖图（硬依赖 →；软依赖 ~>，软依赖缺席时降级）：

```
projects → core
issues → projects, labels, statuses
comments → issues ~> attachments（无附件时 composer 降级）
activities → issues
attachments → issues ~> billing（配额 port 无 billing 时无限制）
webhooks → core ~> issues（事件类型）
notifications → core, issues
search → issues, comments
favorites → issues, projects
relations → issues
notifications → issues（`issue-subscriptions` 资源并入 notifications：notification dao 直接使用订阅表）
project-updates → projects
cycles → projects
recurrences → issues, cycles, notifications, labels, statuses
roadmap → projects, cycles
views → projects ~> billing
templates → issues, projects, labels, statuses
billing → core
api-keys → core
public-api → api-keys, issues, labels, projects
capabilities → issues, projects, comments, labels, statuses, activities,
               relations, views, cycles, project-updates, search, favorites,
               templates, recurrences（即 Tier 1+2 全集）
ai → capabilities ~> billing
mcp → capabilities, core（OAuth 经 better-auth）
```

> `capabilities` 当前 `CapabilityDeps` 硬性要求全部 15 个 service（`capabilities/types.ts`）。本方案允许其作为整体存在或缺席，**不做逐条能力的细粒度裁剪**（未来可演进为每条能力声明 `requires`，见 §13 风险 R7）。

### 2.4 Preset 定义

| Preset | 特性集 | 定位 |
|--------|--------|------|
| `minimal` | core + Tier 1 | 干净的账号/组织/项目/issue/评论底座 |
| `collaboration` | minimal + Tier 2 collaboration | 加附件、webhook、通知、搜索 |
| `planning` | minimal + Tier 2 planning | 加周期、路线图、迭代 |
| `saas` | minimal~planning + billing + api-keys + public-api | 商业化底座 |
| `ai` | 任意 + capabilities + ai + mcp | 智能化（通常叠加在 saas 上） |
| `full` | 全部 | 模板仓库自身 |

Preset 只是**起点**，脚手架同时允许用户增删单个特性（在依赖图约束内）。

### 2.5 目标目录结构

```
react-hono-template/
├── presets/                          # ★ 新增：声明式清单（脚手架唯一事实源）
│   ├── schema.ts                     # manifest/preset/feature 的 zod schema
│   ├── features/                     # 每特性一份 <id>.json（env 契约、文件声明、绑定需求）
│   └── presets/                      # minimal.json / ai.json / full.json …
├── apps/
│   ├── api/src/
│   │   ├── core/                     # Tier 0：平台底座（不可裁剪）
│   │   │   ├── auth/  db/  lib/  middleware/  platform/
│   │   │   ├── controllers/ services/ dao/ dto/ routes/   # 仅 core 自身资源
│   │   │   └── compose.ts            # composeModules：折叠器
│   │   ├── features/
│   │   │   ├── issues/
│   │   │   │   ├── module.ts         # ★ ApiFeatureModule 实现
│   │   │   │   ├── schema.ts         # 本特性表定义（dialect 参数化）
│   │   │   │   ├── dao/ services/ controllers/ routes/ dto/
│   │   │   │   └── public-api.ts     # v1 路由贡献（可选）
│   │   │   ├── ai/                   # 原 ai/ + mcp/ + capabilities 适配 + ai-* 服务
│   │   │   ├── billing/              # 原 billing/plan/quota/stripe + storage-usage
│   │   │   └── …（每个特性同构）
│   │   ├── app.ts  index.ts  queue.ts  scheduled.ts  serve.ts  server.ts
│   │   └── manifest.ts               # 从 presets/ 生成（模板仓库 = 全量）
│   ├── web/src/
│   │   ├── features/
│   │   │   ├── registry.ts           # ★ WebFeatureModule 注册表（模板仓库手维护，脚手架裁剪）
│   │   │   └── <feature>/（data.ts + components/ + locales/en.ts + locales/zh.ts）
│   │   └── core 基础设施不变（lib/ components/ i18n 组装器/ routes/）
│   └── …
├── packages/
│   ├── shared/src/
│   │   ├── core/                     # api-error/api-result/constants/pagination/csv
│   │   └── features/<feature>/       # 该特性的 schemas/plans 片段
│   └── ui/                           # 不变（无业务知识）
└── docs/
```

**分层规则演进**：`controller → service → dao → db` 在**特性内部**原样保留；新增两条边界规则：

1. `features/<a>` 不得 import `features/<b>` 的内部实现，只能经 `compose.ts` 提供的注册表按 port 交互（少数领域强关联允许显式依赖，如 issues → labels，须在 manifest 声明并被拓扑校验）；
2. `core/` 不得 import `features/**`（反向即架构违规，Phase 0 加检查）。

### 2.6 每阶段完成定义（DoD）

所有 Phase 共同的 DoD：

- `bun run check`、`bun run typecheck`、`bun run build`、`bun run test` 全绿；
- `AGENTS.md` 与 `docs/架构.md` 同步更新；
- 不留废弃路径的兼容 re-export 超过一个 PR 周期。

## 3. Feature Module 接口设计

> 以下 TypeScript 为**设计契约**，实现时允许微调命名，但槽位语义不得增减。

### 3.1 ApiFeatureModule

```ts
// apps/api/src/core/compose.ts

/** 挂载阶段——与现有 routes.ts / app.ts 的顺序约束一一对应，顺序即数组成员序 */
type MountPhase = "public" | "me" | "admin" | "org" | "app";

type ApiFeatureContext = {
	db: Database;
	cache: CacheStore;
	storage: StorageAdapter | null;
	background: BackgroundFn;
	core: CoreRegistry;            // core 服务（auth、org、member、audit、config…）
	registry: ContributionRegistry;// 各特性贡献的汇总视图（见下）
	env: ResolvedEnv;              // 按 manifest 校验后的 env 快照
};

type ApiFeatureContribution = {
	/** 供其他特性和 compose 后导出的 DAO 工厂结果 */
	daos?: Record<string, unknown>;
	services?: Record<string, unknown>;
	/** 路由贡献；phase 决定挂载时机（org 阶段保证在 org 中间件之后） */
	routes?: Array<{ phase: MountPhase; create: (ctx: ApiFeatureContext) => Hono }>;
	/** v1 公共 API 子应用的路由贡献（public-api 特性聚合） */
	publicApiRoutes?: Array<(ctx: ApiFeatureContext) => Promise<Hono>>;
	/** 能力注册（capabilities/ai/mcp 链） */
	capabilities?: (ctx: ApiFeatureContext) => CapabilityEntry[];
	/** 周期清理钩子（并入 cleanup cron） */
	cleanupHandlers?: Array<(now: Date) => Promise<Record<string, number>>>;
	/** 定时任务（独立 try/catch，互不影响——沿用 handleScheduled 现有模式） */
	scheduledJobs?: Array<{ name: string; run: (now: Date, background?: BackgroundFn) => Promise<unknown> }>;
	/** 队列消费者（webhooks → WEBHOOK_QUEUE） */
	queueConsumers?: Array<{ queue: "webhook"; handle: MessageHandler }>;
	/** 配额计量贡献（billing 关闭时无人消费） */
	quotaMeters?: MeterId[];
	/** 冻结组织的写豁免路径（billing、ai/chat） */
	freezeWriteExempt?: string[];
	/** 组织创建后的初始化钩子（statuses.ensureDefaultStatuses） */
	onOrgCreated?: Array<(orgId: string) => Promise<void>>;
	/** 事件处理注册（webhooks 派发、notifications 投递——见 Phase 1 EventSink port） */
	eventHandlers?: DomainEventHandler[];
};

type ApiFeatureModule = {
	id: string;
	dependsOn: string[];           // 硬依赖，compose 时拓扑排序 + 校验
	softDependsOn?: string[];      // 软依赖，缺席时特性内部走 no-op port
	/** env 契约声明（fail-closed 语义不变，只是集中声明） */
	env?: { required: string[]; optional: string[]; mockFlag?: string };
	register: (ctx: ApiFeatureContext) => ApiFeatureContribution | Promise<ApiFeatureContribution>;
};

type ComposedApp = {
	app: Hono;                      // 已挂载全部路由与中间件
	dependencies: Dependencies;     // 兼容现有导出形状
	scheduledJobs: ScheduledJob[];
	queueConsumers: QueueConsumer[];
};

composeModules(manifest: FeatureManifest, platform: AppPlatform): ComposedApp;
```

挂载阶段与现有代码的对应（保证行为不变）：

| Phase | 现有代码位置 | 内容 |
|-------|-------------|------|
| `public` | `routes.ts` 头部 | media、bootstrap、config、oauth 登录 |
| `me` | `.use("/api/me/*", requireAuth)` 之后 | me-media |
| `admin` | `.use("/api/admin/*", requireAuth)` 之后 | admin 路由 |
| `org` | `.use("/api/orgs/:orgId/*", requireAuth, requireOrgMember)` 之后 | MCP 路由 + 全部资源路由 |
| `app` | `app.ts` 顶层 | `/mcp` 端点、`/.well-known/*`、Stripe webhook、`/api/v1` |

折叠器按 `(phase 序, manifest 声明序)` 稳定排序挂载，**org 中间件永远先于 org 阶段路由**——此顺序写进回归测试（现有 routing 测试基础上补一条断言）。

### 3.2 WebFeatureModule

```ts
// apps/web/src/features/registry.ts

type WebFeatureModule = {
	id: string;
	/** 组织侧边栏导航项（合并进 ORG_SIDEBAR_NAV 渲染） */
	nav?: OrgSidebarNavItem[];
	/** 命令面板动作（合并进 PALETTE_ACTIONS） */
	paletteActions?: PaletteAction[];
	/** 设置页导航（settings 布局渲染） */
	settingsNav?: SettingsNavItem[];
	/** 挂在 org-layout 的全局 Provider（ChatProvider 等） */
	providers?: React.ComponentType<{ children: React.ReactNode }>[];
	/** landing 页分节（按序渲染） */
	landingSections?: LandingSection[];
	/** 本特性的 i18n 命名空间文件（locales/<lang>/<ns>.ts） */
	i18nNamespaces?: string[];
	/** 全局快捷键声明 */
	hotkeys?: HotkeyBinding[];
};
```

模板仓库中 `registry.ts` 手工维护全量列表；脚手架按 manifest 裁剪条目。`org-sidebar-nav.ts`、`command-palette/actions.ts`、settings 布局、`org-layout.tsx` 改为**读注册表**而不是各自硬编码。

### 3.3 SharedFeature 子路径

```
packages/shared/src/
  core/    → api-error, api-result, constants, pagination, csv
  features/issues/  → schemas/issue.ts, schemas/issue-query.ts, …
  features/ai/      → schemas/ai.ts, ai 计量常量
  features/billing/ → plans.ts, quota.ts, schemas/billing.ts
  index.ts          # 全量 re-export（模板仓库形态）
```

脚手架裁剪 `features/<未启用>/` 目录并重写 `index.ts`。API 与 web 的同次生成物始终裁剪一致，类型链天然自洽。

### 3.4 Manifest 与 Preset 格式

```jsonc
// presets/features/ai.json —— 特性声明（文件声明供 CI 覆盖率校验，见 §11）
{
  "id": "ai",
  "tier": 4,
  "dependsOn": ["capabilities"],
  "softDependsOn": ["billing"],
  "env": {
    "required": [],
    "optional": ["AI_BASE_URL", "AI_API_KEY", "AI_MODEL"],
    "mockFlag": "AI_PROVIDER=mock"
  },
  "claims": [                                    // 本特性拥有的路径（glob）
    "apps/api/src/features/ai/**",
    "apps/web/src/features/ai/**",
    "packages/shared/src/features/ai/**",
    "apps/web/src/routes/_auth/orgs/$orgId/ai.*",
    "apps/web/src/routes/_auth/orgs/$orgId/settings/ai.tsx",
    "docs/AI与MCP.md"
  ]
}

// presets/presets/minimal.json
{
  "name": "minimal",
  "features": ["core", "projects", "issues", "labels", "statuses", "comments", "activities"],
  "platform": ["cloudflare", "bun-selfhost"],
  "docs": ["README.md", "docs/本地开发.md", "docs/部署.md"]
}
```

`claims` 是脚手架的裁剪依据，也是 CI 的**覆盖率检查**依据：仓库中每个业务路径必须被恰好一个特性声明（core 兜底），防止新文件漏登记（详见 §11）。

### 3.5 环境变量契约

## 7. Phase 3 — Schema 拆分与迁移策略

### 7.1 Schema 拆分

现状：`define-schema.ts` 的 `defineSchema(dialect)` 经 `createSchemaKit(dialect)` 生成双方言表——这个模式**直接保留**，只是把 1758 行按特性切开：

```ts
// features/issues/schema.ts
export const defineIssueTables = (kit: SchemaKit) => {
	const issues = kit.sqliteTable("issues", { ... });
	const issueLabels = kit.sqliteTable("issue_labels", { ... });
	const issueRelations = kit.sqliteTable("issue_relations", { ... });
	const issueSubscriptions = kit.sqliteTable("issue_subscriptions", { ... });
	return { issues, issueLabels, issueRelations, issueSubscriptions };
};

// db/define-schema.ts → 聚合器
export const defineSchema = (dialect: SchemaDialect) => {
	const kit = createSchemaKit(dialect);
	return {
		...defineCoreTables(kit),
		...collectFromModules(manifest, (m) => m.schema?.(kit)),  // 按清单聚合
	};
};
```

51 张表归属见**附录 A**。跨特性外键一直使用显式 `.references()`；拆分后由 `SchemaKit.ref("<sql_table>", "<column>")` 提供**延迟解析的同 slice 引用**（按 SQL 表名登记，drizzle 在生成迁移/内省外键时才求值），因此声明顺序无关、生成的 SQL 与拆分前逐字节一致；relations 定义（`defineRelationsPart`）随表走。实现注记：本项实际落地时 `issue_subscriptions` 表归入 `notifications`（只有 notifications 的 dao/service 使用它），附录 A 以此为准。

### 7.2 迁移策略：放弃挑选历史，改为按 preset 重生成基线

**模板仓库自身**：迁移目录保持线性演进，不动（生产 D1 继续用）。

**生成的项目**：脚手架执行——

1. 按 manifest 聚合 schema 子集；
2. 对空库跑 `drizzle-kit generate`（sqlite + postgres 双方言）产出**单一基线**。drizzle-kit 1.0 RC 的目录格式是 `<14 位时间戳>_<名称>/{migration.sql,snapshot.json}`，没有 `meta/_journal.json`（出现该文件会被 migrator 判成旧格式）；
3. search 特性启用时，追加一个手写迁移目录 `drizzle/<14 位时间戳>_search_fts/migration.sql`，内容就是幂等 FTS DDL（以 `rebuild` 结尾），排在基线之后；`drizzle/fts/search_fts.sql` 只作为运维重放脚本保留；
4. 生成项目从此拥有自己的迁移起点。

模板仓库已经按这种方式落地：`drizzle/20261124084721_init/` + `drizzle/20261124084722_search_fts/`，PostgreSQL 为 `drizzle-pg/20261124084746_init/`。

这绕开了"线性历史不可挑选"与"表重建丢触发器"两个死结：baseline 一次成型，无重建。

### 7.3 FTS 与 search 的特殊处理

- `issue_search` / `comment_search` 虚表 + 6 个同步触发器全部归 search 特性；
- search 缺席时，issues/comments 的写路径不触碰 FTS（触发器不存在即无操作，DAO 无需判断）；
- search 在场时，任何 rebuild issues/comments 的后续迁移后须重跑 FTS DDL——该纪律写入生成项目的 AGENTS.md（与模板一致）。

### 7.4 验收

- 模板仓库 `db:generate` 产物与拆分前**语义等值**（对空库 apply 后 schema dump 对比）；
- 脚手架原型（此阶段用脚本手工跑）对 minimal manifest 生成 baseline，sqlite + pg 双方言均可在本地 apply 并通过测试库初始化。

**工作量**：1–1.5 周。

已核实的跨特性 data 引用（ai→issues/projects、comments→attachments/billing、attachments→billing、activities→members/issues）全部落在依赖图白名单内（§2.3），无需改动，只需在 registry/manifest 声明以便裁剪顺序正确（被依赖特性的 data 先保留）。billing 缺席时 `quota-summary`/升级提示组件不随特性生成，comments/attachments 中对 `features/billing/data` 的 import 由脚手架的**变体补丁**处理：

> 对少数"宿主特性启用而 billing 缺席"的组合，脚手架在裁剪后应用预置的最小补丁（如移除 composer 的配额提示分支）。补丁以显式 diff 文件存于 `presets/patches/`，数量预计 ≤5 个，逐个评审维护。这是全方案唯一允许"补丁"的地方，宁少勿多。

### 9.5 landing 页与 onboarding

- `pages/landing.tsx` 分节化：每节由特性贡献（`landingSections`），minimal 生成物只渲染核心节；
- onboarding 流程不依赖可选特性（现状已如此，验证即可）。

### 9.6 AppType 链路

`hc<AppType>` 的类型来自**同一 manifest 生成的 api**，preset 一致则类型一致，无需额外机制。仅需在 web 测试中补一条：registry 中声明的特性其路由文件必须存在（防手改漂移）。

**工作量**：1.5–2 周。

## 11. Phase 7 — CI Preset 矩阵与发布流程

### 11.1 新增 workflow：`preset-matrix.yml`

- 触发：PR 触及任何被 `claims` 声明的路径（`dorny/paths-filter` 按 claims 动态生成 filter）；
- 步骤：matrix = `[minimal, collaboration, planning, saas, ai, full]`（full 即仓库本身，跳过生成）→ `bun run scaffold --preset <p> --no-git /tmp/out` → 在 `/tmp/out` 跑 `check/typecheck/build/test`；
- 失败即阻塞合并——**这是"模板永远可信"的机制保障**。

### 11.2 claims 覆盖率检查

- 独立 job：遍历 `apps/**/src/features/**`、`packages/shared/src/features/**` 等业务路径，每条路径必须被恰好一个特性 claim（core 兜底清单单独维护）；
- 未声明路径 → 失败并提示登记。防止新文件逃逸出特性体系。

### 11.3 发布节奏

- 模板仓库 `main` = full 形态，语义化版本 tag；
- CHANGELOG 按"特性 × preset 影响"记录（如："billing: quota ledger 变更 → 影响 saas/full"）。

**工作量**：3–5 天 + 持续维护成本（矩阵运行时长纳入 CI 预算，必要时降为每日定时 + 触及路径时增量）。

## 结语

本方案的全部设计都围绕一个原则：**让"特性"成为代码、schema、配置、文案、文档、CI 六个维度上同构的可拔插单元**。Phase 1（依赖倒置）是地基，Phase 2/3（切片与基线）是主体，Phase 4–7 是把模板从"一个仓库"变成"一个生成器"的收口。每一步都以现有质量门为安全网，full 形态行为零变化是贯穿始终的硬约束。

与原始设计的有意偏差（已在对应章节标注）：

1. **`defineSchema` 采用字面 spread** 而非运行时模块收集：返回类型保持精确，`db/schema*.ts` 的 52 个具名导出无需动态类型；代价是新增特性需同步 4 处导出列表（已写入 AGENTS.md 与 presets/README）。

3. **迁移收敛为单一基线**（`drizzle/20261124084721_init` + `*_search_fts`，`drizzle-pg/20261124084746_init`）：从旧模板部署过的环境需重置数据库，步骤见 `docs/部署.md`。

5. **`wrangler` 模板化用 marker 注释**，保留 JSONC 可读性；生成器对成对性、残留绑定做断言。

### 15.1 与 §2–§12 的其余表述差异

以下为实现取舍（代码为准，文档章节保留设计意图）：

1. **模块贡献槽**：实际协议是 `createDaos` + `register` 返回 `{ services, routes, cleanupHandlers, scheduledJobs, queueConsumers, onOrgCreated, freezeWriteExempt, quotaUsageSinks, extras, platform }`；`publicApiRoutes`/`capabilities`/`eventHandlers`/`quotaMeters` 等未实现（capabilities 由模块直接构造，事件通过 ports 注入）。Web 侧实现的是页级 slots（`issueDetailSections`、`projectHeaderActions`、`landingPricing` 等）而非 `landingSections`/`hotkeys` 贡献。
2. **目录形态**：`ai`/`mcp`/`capabilities` 是三个平级切片而非 `features/ai/` 子切片；`packages/shared` 保持扁平 `schemas/*.ts` 而非 `features/<id>/`。
3. **env 契约**：`presets/features/*.json` 的 `env` 字段是文档元数据，尚未驱动启动校验；示例文件用 `@feature:` marker 裁剪。
4. **挂载顺序**：`MountPhase` 是模块元数据，运行时挂载顺序由 `routes.ts` 字面量链决定（有 `route-contributions.test.ts` 防漂移）。
5. **组件归属**：`org-conversation-row`、`quota-error` 按 claims 归 ai/billing，但物理位置仍在 `components/`（裁剪安全）。
6. **脚手架 CLI**：实际为 `--preset/--out/--verify/--force`（无 `--platform`/`--interactive`/`git init`）；生成器只校验硬依赖缺失，不做闭包补全或拓扑重排。
7. **文档子集**：`docs` 列表通过 `extends` 继承（`full` 显式声明全集）；生成器按允许列表删除其余文档并过滤 README/AGENTS 中的引用。
8. **`apps/web/src/components/auth/api-key/**`** 等 Better Auth UI 由对应特性 claim，随特性裁剪。
