# 生产说明

这些是模板有意留下的简化。演示和中小流量下行为是对的。每条后面是 Cloudflare 上继续做实的方向。

## Webhook 投递

写入投递记录后，如果绑定了队列 `react-hono-webhooks`（`WEBHOOK_QUEUE`），就发一条 `{ deliveryId }`。同一个 Worker 消费，每次 HTTP 超时 5 秒，`redirect: manual`。

签名有两套，方便旧接收方过渡：

- 旧头 `x-webhook-signature`：对原始 body 做 hex HMAC-SHA256，没有时间戳，不能防重放
- 标准头 `webhook-id`、`webhook-timestamp`（Unix 秒，每次尝试重新生成）、`webhook-signature`（`v1,<base64>`，HMAC 的内容是 `${id}.${timestamp}.${payload}`）

同时带上 `content-type`、`x-webhook-event`、`x-webhook-delivery`。失败时，`message.attempts` 还没到 2 就 `retry()`；最后一次把记录标成 `failed` 并 ack。`attempts` 从 1 开始，含当前这一次。`max_retries` 是 2。

没有队列绑定时（单测，或配置里拿掉了队列），退回请求内的 `waitUntil`：2 次尝试，5 秒超时，500 毫秒退避。

密钥按原始字符串做 HMAC，不是某些标准库期望的 `whsec_` 前缀。要对接那种库，把 `whsec_` 加上原始密钥的 base64 传进去。密钥明文存储，没有轮换接口。接收方应校验标准签名，并拒绝超出短窗口（例如 5 分钟）的时间戳。

`/api/v1` 上用 API Key 改数据不会写活动日志（没有操作者用户），Webhook 事件仍会发。

## 限流

两档 Workers Rate Limiting：Free 60 次/分钟，Pro 600 次/分钟，按 API Key 哈希分桶。计数在每个 Cloudflare 节点汇总，不是全局精确值，适合套餐权益和防滥用。`wrangler.jsonc` 的限额要和 `packages/shared` 里的 `PLANS` 对齐，绑定限额运行时读不到。

要全局精确计数，改用 Durable Objects。

## 定时任务

同一个 Worker 每 15 分钟跑一次（`*/15 * * * *`）：

- 删掉 `expiresAt` 已过期的邀请；`expiresAt` 为空的保留
- 仍是 `pending`、`attempts = 0`、创建超过 15 分钟的 Webhook 投递，标成 `failed`，`lastError` 为 `delivery timed out`。已经有尝试次数的行留给队列重试
- 已读通知超过 30 天、未读超过 90 天的删除，每轮最多各 500 条。积压会分多轮清完
- 软删除的 Issue 和历史投递记录仍然保留
- 周期 Issue 在这一轮里生成，所以最多比计划时间晚约 15 分钟。生成后通知创建者和负责人，并通过 `waitUntil` 发 `issue.created`。某一次投递失败不会挡住后面的周期任务

## 套餐缓存

套餐变更会清掉当前 isolate 的缓存，以及 KV 的 `cache:v1:plan:<orgId>`。其他节点大约 30–60 秒内跟上（KV 最终一致）。1 小时 TTL 只是写入配额的兜底，漏掉一次失效时，旧限额可能短暂还在。

## 运行时配置

KV 的 `config:global`，进程内缓存 60 秒。写入方自己马上看到新值，其他 isolate 大约 60 秒内跟上。`GET /api/config` 公开，不要放密钥。

## 搜索、导入导出、活动流

全文搜索用 FTS5 的 trigram 索引，短于 3 个字符的词走不上索引，会退回该组织 Issue / 评论上的 `instr()` 扫描。命令面板要求两个字符，更短的中文或英文是最贵的查询。

SQLite 重建表（D1 的实现是建表、拷贝、删除、改名）会丢掉 `issues` / `comments` 上的触发器。任何重建这两张表的迁移之后，都要重跑 `drizzle/fts/search_fts.sql`。步骤在 [部署](部署.md)。

CSV 在一次请求里做完：导出最多 2000 条未归档 Issue，导入最多 100 行。导出里的负责人是显示名。导入按名字解析状态、负责人、标签和周期，坏行会报出来，好行照常导入。更大的量需要分片或队列。

活动流每个 Issue、每个组织只保留最新 100 条。
