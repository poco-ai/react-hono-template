# AGENTS.md

Bun + Turborepo monorepo: Vite/React SPA (`apps/web`) and Hono API (`apps/api`), deployed to Cloudflare Workers by default. The same API also supports self-hosting with Bun, PostgreSQL, Redis and S3-compatible storage. The multi-tenant issue tracker (mini Linear) is the template showcase — see README.md and `docs/` for setup, deployment, and production notes. Focused regression tests live in `apps/api/tests` and `apps/web/tests` and run with Bun (using `node:test`).

## Commands

Package manager is **bun** (`packageManager: bun@1.4.2`, `bun.lock`). Do not use npm/pnpm/yarn.

- `bun install`
- `bun run dev` — turbo dev: runs web (Vite on :5173) and api (`wrangler dev` on :8787) together. Web proxies `/api` → :8787, so both must be running for local API calls.
- `bun run test` — API auth/quotas/routing and web feature-data/cache/URL/architecture regression tests; web tests preload a minimal language-detection environment
- `bun run check` — `biome ci .` (format + lint + assist, read-only; the CI gate)
- `bun run lint` — `biome lint .` (Biome, not ESLint)
- `bun run format` — `biome format --write .`
- `bun run typecheck` — turbo typecheck across all packages (web uses `tsc -b` project references and includes `tests` via `tsconfig.test.json`; others `tsc --noEmit`)
- `bun run build` — turbo build (builds `web` only; api deploys from source, wrangler bundles it)

Single workspace: run the script from inside the app/package dir, or `bunx turbo dev --filter=api`.

Pre-commit (husky + lint-staged) runs `biome check --write` on staged files.

## Layout

- `apps/api` — Hono on Cloudflare Workers. Entry `src/index.ts` (default export). D1 binding `DB` via drizzle-orm; better-auth mounted at `/api/auth/*`; public API sub-app in `src/features/public-api/` mounted at `/api/v1`; Stripe webhook at `/api/stripe/webhook`. Platform foundation lives in `src/core/` and each business capability is a self-contained slice under `src/features/<id>/` wired by a feature-module registry (`src/manifest.ts` → `src/core/compose.ts`). Inside every slice the layering is still controller → service → dao → db, see "API (apps/api)".
- `apps/web` — React 19 + Vite SPA (Tailwind v4), deployed as static Workers assets with SPA fallback — its `wrangler.jsonc` has no `main`/Worker script.
- `packages/shared` — zod request schemas (used by both API validation and web forms), plan limits (`PLANS`), issue/webhook constants, error codes, `ApiResult` envelope. No build step.
- `packages/ui` — shadcn/ui components (Base UI, style "base-nova"), plus a `ColorSwatchPicker` (fixed swatch palette with radio-group semantics) used for project and label colors. No build step.

`@workspace/shared` and `@workspace/ui` package exports point directly at TS source — edits take effect immediately, no build needed.

`apps/web` imports API route types via the `@api/*` tsconfig path alias (`AppType` from `apps/api/src/routes.ts`, used by `hono/client` in `apps/web/src/lib/api.ts`). Type-level only; runtime calls go through `VITE_API_URL` or the `/api` proxy.

## API (apps/api)

- Env files (both gitignored):
  - `.dev.vars` — local Worker settings; copy from `.dev.vars.example`. Attachment uploads need S3-compatible storage; the standalone RustFS steps and `S3_*` values are in `docs/本地开发.md`. Without storage, uploads return 503. `S3_SIGNING_ENDPOINT` is optional when browsers and the API reach the same bucket at different URLs.
  - `.env` — drizzle-kit remote D1 credentials for `db:push` (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, `CLOUDFLARE_D1_TOKEN`), or self-hosted Bun settings (copy `env.server.example`). `db:migrate:remote` uses Wrangler authentication instead of the drizzle-kit token.
  - Prod secrets: `bunx wrangler secret put <NAME>` (never put them in `wrangler.jsonc`)
- `worker-configuration.d.ts` is generated. After editing `wrangler.jsonc` (e.g. new bindings), run `bun run cf-typegen`; never edit it by hand. Optional env vars are declared in `src/env.d.ts`.
- KV binding `KV` (`kv_namespaces` in `wrangler.jsonc`) backs runtime config (public `GET /api/config`, admin `PUT /api/admin/config`, key `config:global`, L1 cache 60s), label lists (`cache:v1:labels:<orgId>`) and plan caches (`cache:v1:plan:<orgId>`). Label/plan entries use 1h fallback TTLs but are invalidated explicitly on label writes and billing changes — the long TTL only protects the KV write quota. Local KV is simulated by `wrangler dev`; the namespace must exist before deploy (the CI `CLOUDFLARE_API_TOKEN` needs Workers KV permission).
- Drizzle schema: each slice owns `features/<id>/schema.ts` (`define<Feature>Tables(kit)`), core owns `src/core/schema.ts`, and `src/db/define-schema.ts` only spreads them per dialect; `src/db/schema.ts` selects the runtime schema and `src/db/auth-schema.ts` exports Better Auth definitions. For D1: `bun run db:generate` → `bun run db:migrate:local`; for PostgreSQL: `bun run db:generate:pg` → `bun run db:migrate:pg`. `db:migrate:remote` and `db:push` operate on real remote D1 — do not run casually.
- Migration history is a **single baseline** (the template is a fresh start): SQLite `drizzle/20261124084721_init/` (generated from the current schema) + `drizzle/20261124084722_search_fts/` (hand-written FTS DDL), PostgreSQL `drizzle-pg/20261124084746_init/`. `pg_trgm` indexes stay outside migrations: `src/db/migrate-pg.ts` runs `drizzle-pg/fts/search_trgm.sql` after migrating. drizzle-kit 1.0 RC stores one folder per migration (`<14-digit-timestamp>_<name>/{migration.sql,snapshot.json}`) and has **no `drizzle/meta/_journal.json`** — creating one makes `readMigrationFiles` throw `old drizzle-kit migration folders`. Never edit an applied migration; add a new timestamped folder with `bun run db:generate` / `db:generate:pg`, and expect a second generate on a clean tree to say "No schema changes" (a folder without `snapshot.json` is fine only for hand-written DDL like FTS; if generate re-emits existing tables, the snapshot chain is broken). Environments deployed from the older template must reset their database — see `docs/部署.md` 从旧模板升级.
- Full-text search (FTS5): `drizzle/20261124084722_search_fts/` creates the `issue_search`/`comment_search` virtual tables and six sync triggers; `drizzle/fts/search_fts.sql` is the re-runnable copy of that DDL (idempotent, ends with `rebuild`). SQLite table rebuilds (D1 implements them as create/copy/drop/rename) silently drop triggers on `issues`/`comments`, so **after any migration that rebuilds either table, re-run** `bunx wrangler d1 execute DB --local --file=drizzle/fts/search_fts.sql` (and `--remote` for prod) to restore the triggers and re-index. Never use `db:push` to skip this; `apps/api/tests/search*.test.ts` assert the six triggers exist and run an FTS integrity check — if search starts returning stale results, suspect a lost trigger before anything else.
- Tests run against the real migrations through `tests/helpers/test-db.ts` + `fixtures.ts`; do not add hand-written DDL or batch shims.
- Path params: declare every URL segment in `src/core/lib/params.ts` schemas and attach `validate(..., "param")` after the org/role middleware. Hono infers the web client's param type from `c.req.valid("param")`, so omitting a parent segment (`orgId`/`projectId`) breaks web types; controllers read `c.req.valid("param")`.
- `src/core/lib/db-errors.ts` is the only UNIQUE-constraint matcher (drizzle wraps the SQLite error in `cause`); never regex `err.message`.
- Cache business payloads through `src/core/lib/kv/resource-cache.ts` (per-isolate L1 + KV). Never cache auth/session/permission data; L1 entries are not evicted across isolates.
- Webhook retries belong to Cloudflare Queues (`max_retries: 2`, `retry_delay`, DLQ `react-hono-webhooks-dlq`). The consumer claims each attempt with `claimAttempt` before POSTing; do not add in-request sleep retries.
- Layering inside a slice (strictly one direction: `controller → service → dao → db`; dto is referenced by all layers):
  - `features/<id>/controllers/` — HTTP handlers: receive validated input (zod via `src/core/lib/validation.ts`, wired in resource routers), call service, wrap with `ok`/`fail` from `src/core/lib/response.ts`. Keep them thin.
  - `features/<id>/services/` — business logic; throw `ApiError` (from `@workspace/shared`) for domain failures, mapped to responses by the `onError` handler in `src/routes.ts`. Services take a `background` callback (from `src/core/lib/background.ts`, wired in controllers via `c.executionCtx`) for webhook dispatch — never import hono types here.
  - `features/<id>/dao/` — the only business layer allowed to use drizzle/SQL; `createXxxDao(db)` factory pattern. Await Drizzle queries directly; for one row, use `.limit(1)` on a select or destructure the first row from `.returning()` on a write. D1-specific `.get()`/`.all()` are not available under PostgreSQL. Use `runBatch` from `src/db/run-batch.ts` for multi-write atomicity; build every statement using its callback's database handle (D1 batch / PostgreSQL transaction). Shared cross-feature SQL helpers live in `src/core/dao/` (`search-sql.ts`, `progress-sql.ts`, `activity.dao.ts`).
  - `features/<id>/dto/` — request/response types (`XxxDto`, derived from `$inferSelect`).
  - `src/core/lib/` — framework helpers (response envelope, validation, better-auth factory, KV cache, background); `src/core/middleware/` — `requireAuth`/`requirePermission` (platform), `requireOrgMember`/`requireOrgRole` (org scoping + freeze check); `src/core/platform/` — Cloudflare vs self-host bindings.
  - `src/core/lib/ports/` — **structural port types** (`WebhookDispatcher`, `IssueNotifications`, `PlanSource`, `QuotaUsageSink`, `CleanupHandler`, `CycleGuard`, …) shared across slice boundaries. Core and Tier-1 services depend only on these, so a feature can be trimmed from a preset without breaking its consumers. Port implementations are injected at assembly time; no-op/static defaults exist for optional integrations.
  - `src/features/<id>/module.ts` — the slice's registration protocol: `createDaos(ctx)` contributes its DAOs (phase A), `register(ctx)` returns `{ services, routes, cleanupHandlers, scheduledJobs, queueConsumers, onOrgCreated, freezeWriteExempt, quotaUsageSinks }` (phase B). Cross-feature access goes through `ctx.features.get<OtherContribution>(id)` or `ctx.daos` — never by importing another slice's internals.
  - `src/core/compose.ts` — the feature-agnostic combiner; it must never import `features/**`. It builds all DAOs first (they only need `db`), then registers services in manifest order, then folds routes at the historical mount phases (`public` → `me` → `admin` → `org` → `app`).
  - `src/manifest.ts` — the ordered `FEATURE_MODULES` list; this is the scaffold's single injection point (the template ships the full set). `dependencies.ts` and `routes.ts` are thin facades over the composition that keep the `Dependencies` / `AppType` exports stable.
  - `src/routes.ts` stays a **literal Hono chain** — Hono's `hc<AppType>` inference cannot survive a runtime fold. Feature modules still declare route contributions as scaffold metadata; `tests/route-contributions.test.ts` pins the two views together.
  - To add a resource: add the slice under `features/<id>/` (module.ts + `schema.ts` tables via `SchemaKit`, cross-slice foreign keys through `kit.ref("<sql_table>", "<column>")`, plus the four literal schema export points — `db/define-schema.ts` spread, `db/schema.ts`, `db/schema.sqlite.ts`, `db/schema.pg.ts`) and migrations for both dialects; dto/dao/service (plan-limit checks via `src/core/services/plan.service.ts`, webhook `dispatch` via the `WebhookDispatcher` port), controller, router; register it in `src/manifest.ts` and the literal chain in `src/routes.ts`; add zod schemas in `packages/shared/src/schemas/`; declare the feature in `presets/features/<id>.json` (claims + deps).
- Feature manifests (`presets/`): `presets/features/*.json` declare each feature's id, tier, `dependsOn`/`softDependsOn`, env contract and `claims` (glob ownership). `presets/presets/*.json` compose them (`minimal`, `collaboration`, `planning`, `saas`, `ai`, `full`). `apps/api/tests/architecture.test.ts` enforces claims coverage, dependency boundaries (`core/**` never imports `features/**`) and preset hard-dependency closure. See `presets/README.md` for the ownership rules.
- Org scoping: all business routes live under `/api/orgs/:orgId/*` behind `requireAuth` + `requireOrgMember` (404 for non-members, 403 `ORG_FROZEN` for writes when frozen — reads and `/billing` stay open); org-role writes use `requireOrgRole("owner","admin")`.
- Public API: `src/features/public-api/` is a separate `OpenAPIHono` app (bearer API keys, `src/features/api-keys/middleware/api-key.ts`) mounted in `src/app.ts` — deliberately outside the `AppType` chain. It reuses the same dao/service layers. Rate limiting uses the `RATE_LIMITER_FREE`/`RATE_LIMITER_PRO` bindings in `wrangler.jsonc` — keep their limits in sync with `PLANS` in `packages/shared`.
- Billing: `src/features/billing/` (`billing.service.ts`, `quota.service.ts` ledger, `storage-usage.service.ts`) + `src/features/billing/lib/stripe.ts`. Plan-name resolution is `src/core/services/plan.service.ts` (PlanSource port; billing injects the DB-backed source). Without any `STRIPE_*` vars it's mock mode **only if `BILLING_MOCK_MODE=true`** (local `.dev.vars` only; never in `wrangler.jsonc` — `apps/api/tests/config-safety.test.ts` enforces this); partial Stripe config fails closed with 503. Plan quotas (members incl. pending invitations, orgs per user) live in `src/core/services/auth-policy.service.ts`; better-auth hooks in `src/core/lib/auth.ts` invoke this service and translate domain errors to auth responses, including frozen-organization writes and admin self-role/ban guards.
- Password reset: better-auth's `sendResetPassword` (`createResetPasswordSender` in `src/core/lib/auth.ts`) sends the link through Resend when configured; without a provider it logs only when `AUTH_ALLOW_INSECURE_LOGGING=true` (local only) and otherwise fails closed so reset tokens never reach production logs.
- Email OTP sign-in: better-auth's `emailOTP` plugin in `src/core/lib/auth.ts` issues 6-digit, 5-minute codes and sends them through Resend (`src/core/lib/email.ts`, `RESEND_API_KEY` + `EMAIL_FROM`; set both or neither, partial config fails). Without them the code is logged only with `AUTH_ALLOW_INSECURE_LOGGING=true`, otherwise delivery fails closed. `disableSignUp: true` restricts the flow to existing accounts. The registry adapter lives in `src/core/lib/auth/email-otp-plugin.ts` and the web route is `/email-otp`.
- Bootstrap: the first registered user becomes admin only when `ALLOW_FIRST_USER_ADMIN=true` (local/self-hosted). Promotion is a single conditional UPDATE so concurrent sign-ups cannot create multiple admins. Production should provision admin roles explicitly. Emails are not auto-verified; verification links go through Resend (`emailVerification.sendVerificationEmail`, web route `/verify-email`), and OTP sign-in / OTP password reset also mark the address verified. Invitation acceptance is possession-based on the opaque `invitationId`, while `list-user-invitations` remains gated on a verified email.
- CORS and Better Auth use `TRUSTED_ORIGINS`, a comma-separated list of frontend origins. If omitted, `src/core/platform/origins.ts` supplies local development and demo defaults.
- drizzle-orm/drizzle-kit are 1.0 RC; `skipLibCheck` in tsconfig is required for their types — don't remove it.
- D1 batch caveat: `db.batch()` returns rows keyed by column NAME (D1 has no array mode), so duplicate SQL column names across joined tables collapse and shift every value (drizzle-orm#6038). Single queries map correctly. Any select that joins another table must alias the joined columns to unique names with `.as()` (see `COMMENT_SELECT` in `src/features/comments/dao/comment.dao.ts`) — including before moving an existing joined select into a batch.

## AI & MCP (apps/api, apps/web)

- **One capability layer, two surfaces.** `apps/api/src/features/capabilities/` defines framework-neutral read/write capabilities (zod input, effect, scopes, role, executor). `apps/api/src/features/ai/tools.ts` adapts them to AI SDK tools; `apps/api/src/features/mcp/tools.ts` adapts them to MCP tools. Business logic stays in services; adapters must not add authorization logic. AI writes/destructive tools use AI SDK approval in chat; MCP writes are scope-gated and blocked when the organization enables `strict_mcp_writes`.
- **AI provider.** `apps/api/src/features/ai/provider.ts` supports `mock` (offline, deterministic) and `openai-compatible` (`AI_BASE_URL`/`AI_API_KEY`/`AI_MODEL`; all required, fail closed with `AI_NOT_CONFIGURED`). Model-facing prompt text is English; replies follow the request locale. `AI_ENABLED` is global, org enablement is in `org_ai_settings`. Plan quotas live in `packages/shared/src/plans.ts`; chat usage is recorded per org/user/day in D1, MCP uses the plan API rate limit.
- **Chat.** `/api/orgs/:orgId/ai/*` is session-auth. `POST /ai/chat` streams AI SDK UI messages, persists user/assistant messages and tool calls, verifies approval responses against stored proposed calls (including the input hash), and never trusts client-provided system messages. Conversation detail is owner-scoped; admins see aggregate usage only.
- **MCP.** `POST /mcp` is a stateless `createMcpHandler` (v2) endpoint. API keys (`sk_...`) are org-pinned and scope-filtered; OAuth uses better-auth `mcp()` + `jwt()` with `/api/auth/oauth2/*`, JWKS and the web `/consent` page. `MCP_DCR_ENABLED` is local/dev only; production should use CIMD or pre-provisioned clients. `MCP_RESOURCE` is the token audience and must match the public `/mcp` URL.
- **Workers constraint.** The auth instance is created lazily in `src/app.ts` because the MCP OAuth plugin seeds an `oauth_resource` row during init and Workers disallow D1 I/O at module scope. Do not move `createAuth` back to top-level. `activities.source`/`source_id` are reserved for source attribution; tool-call audit lives in `ai_tool_calls`.
- **Web.** `features/ai/data.ts` owns conversation/usage/settings queries, cache keys and the AI SDK transport. `chat-provider.tsx` owns the single stream shared by the side panel and `/ai` page; views must not create their own `useChat`/transport. Consent/MCP settings live in `features/mcp/data.ts`. All labels go through i18n (`en.ts` is the source of truth).
- **Env/docs.** `AI_*`, `APP_WEB_URL`, `MCP_*` and rate-limiter bindings are declared in `src/env.d.ts`/`wrangler.jsonc`; keep `AI_*` examples in `.dev.vars.example`. Never commit provider keys. `bun run cf-typegen` after binding changes.

## Web (apps/web)

- API base URL is `import.meta.env.VITE_API_URL`, baked in at build time (CI sets it to the prod API URL). Unset in dev, so `hc<AppType>("")` relies on the Vite `/api` proxy. `lib/api.ts` exports `unwrap` (throws Errors carrying the API `code`, e.g. for `isPlanLimitError`).
- Routing: TanStack Router, file-based (`src/routes/`, `routeTree.gen.ts` is generated by vite build — commit it, never hand-edit, and excluded from biome). Guards live in route `beforeLoad` (`_auth` session guard, org layout membership check, admin/owner role checks); list/filter state belongs in URL search params validated with zod. `useSearch` takes the route id (`/_auth/...`), `useNavigate` the URL path. `/` is public (`routes/index.tsx`): `beforeLoad` loads the session and the route renders the marketing landing page (`pages/landing.tsx`) for signed-out visitors, or `HomePage` (which redirects to the first org / `/onboarding`) when signed in. Auth pages outside `_auth`: `/login`, `/email-otp`, `/register`, `/forgot-password`, `/reset-password`; the account page is `/account` behind `_auth`.
- **Feature data convention (all domains):** `src/features/<feature>/data.ts` is the single data-layer entry point. Keep domain types/constants, canonical query keys, query/infinite-query factories, requests, mutation hooks and cache policies together there. This applies to simple and complex domains alike; do not recreate `lib/queries/` or scatter business `useMutation`/request/cache logic in UI files. Do not create empty companion `api.ts`/`queries.ts`/`mutations.ts`/`cache.ts` files just to match a template. If a module eventually needs internal splitting, keep `data.ts` as the stable consumer entry point.
  - Domains: `auth`, `organizations`, `members`, `projects`, `issues`, `comments`, `attachments`, `activities`, `labels`, `api-keys`, `webhooks`, `billing`, `admin`. Session/bootstrap factories and auth writes belong to `features/auth/data.ts`; the SDK/client setup stays in `lib/auth-client.ts`/`lib/api.ts`.
  - Pages/routes/components consume query factories and mutation hooks from the owning `data.ts`. UI owns form parsing, local state, enable/open conditions, navigation, dialogs and translated toast/error presentation. Pass validated values as mutation variables, rather than reading form state inside requests. Optional mutation callbacks are for UI effects; they must not replace the feature's request, optimistic update or cache invalidation policy (`lib/mutation-callbacks.ts` restricts these options).
  - Query keys preserve the `["orgs", orgId, ...]` hierarchy and existing filter/pagination dimensions. Cross-module key factories live in `features/keys.ts`, which must stay import-free; keys that need domain types (`IssueFilters`, `CycleStatusFilter`, `NotificationFilter`, `SearchRequest`) stay in their owning `data.ts`. Invalidate resource prefixes to cover all pages/filters. Global organization-list invalidation may use `exact: true` when a write should refresh the list without invalidating other organizations' resource caches.
  - Mutation hooks own request/error-code propagation, optimistic updates/rollback and related-cache invalidation. Use `lib/feature-mutation.ts` (`useInvalidatingMutation`) for the common "invalidate on success + forward UI callbacks" shape, and `lib/optimistic-mutation.ts` (`useOptimisticMutation`) with `optimisticPatch` from `lib/optimistic.ts` for multi-key snapshots/rollback. Issue writes refresh project/list/detail and activity caches; comment/attachment writes refresh their own list and issue/org activity feeds; label changes refresh issue displays; webhook writes refresh delivery pages too. Preserve partial-bulk failure handling, upload AbortSignals, one-time secrets and billing redirect behavior. Run cache policies even when the initiating component unmounts; UI callback delivery follows TanStack Query's hook/per-call semantics.
  - Forms go through `lib/use-zod-form.ts` (TanStack Form wrapper); `lib/zod-i18n.ts` installs the zod error map and must load before any schema parse. Do not hand-roll `useState` + `setFieldErrors` forms. Page-count/next-page math lives in `lib/pagination.ts`; bulk selection in `lib/use-bulk-selection.ts`.
  - Global shortcuts are declared in `lib/hotkeys.ts` and registered with `useHotkey`/`useHotkeys` under the `HotkeysProvider` in `main.tsx`. Do not add `window` keydown listeners; use `isHotkeyBlocked()` for modal gating and leave input handling to `ignoreInputs: "auto"`.
  - Virtualize only unbounded lists (`useWindowVirtualizer` in the org activity feed); paginated tables/boards keep normal DOM for table semantics, sticky headers and drag targets. Off-screen virtual rows are not in the DOM, so Tab/Ctrl+F only reach rendered rows.
  - Mentions render through `lib/remark-mentions.ts` (mdast transform). Never pre-rewrite markdown strings or hand-scan code fences; the editor keeps its textarea + cmdk picker and uses the helpers in `lib/mention.ts`.
  - Command palette actions are declared per feature in `features/<id>/web.ts` (`paletteActions`), with the shell shortcuts in `components/command-palette/actions.ts`; render them from data rather than duplicating `CommandItem` blocks.
  - Feature data modules may depend on other feature data modules when required by cache/domain relationships, but keep imports acyclic. They must never import UI components, pages or routes. `lib/` is reserved for shared infrastructure and generic utilities. URL search schemas (e.g. `features/issues/search.ts`) are separate from server-state data.
- **Web feature registry (Phase 5):** `src/features/<id>/web.ts` declares what a feature contributes to the global shell — `nav` (workspace sidebar), `paletteActions` (command palette), `settingsNav` (org settings tabs), `providers` (global providers such as the AI chat), `mobileTabs` (bottom bar), `sidebarSections` (extra sidebar content such as the AI chat list), `projectExtras` (per-project rows), `panels` (fullscreen panels such as the chat panel), `palettePanel` (hook that opens a feature panel from the palette) and `i18nNamespaces` — typed by `features/web-types.ts`. `features/registry.ts` is the literal aggregation point (the web mirror of `apps/api/src/manifest.ts`): the scaffold rewrites it per preset, so a trimmed feature removes every contribution at once. The shell (`org-sidebar-nav.ts`, `command-palette/actions.ts`, `org-settings-nav.ts`, `org-layout.tsx`, `org-sidebar-projects.tsx`, `mobile-tab-bar.tsx`) keeps only core entries and merges the registry through `mergeSidebarNav`/`mergePaletteActions`/`mergeSettingsNav`/`mergeMobileTabs`/`webProviders`/`webSidebarSections`/`webProjectExtras`/`webPanels`/`webPalettePanel`; the shell owns the render order (`*_ORDER` maps, because one feature can contribute non-adjacent entries) and `orgSidebarNav()` resolves lazily to avoid the registry↔sidebar import cycle. `tests/web-registry.test.ts` pins the merged ids/labels/order to the pre-refactor implementation and checks that every `web.ts` id exists in `presets/features/`.
  - Shell files must never import a feature module directly (`useAiChat`, `unreadCountQuery`, …): route the dependency through a registry contribution. `components/` files claimed by a feature are pruned with it; unclaimed files are core shell and must compile with any supported preset. `web-types.ts` route unions (`OrgSidebarNavTo`, `SettingsNavTo`, `MobileTabTo`) list every possible route, so the scaffold rewrites them per preset.
  - The shell baseline presets must satisfy: `minimal` includes `projects` (`org-layout` project sidebar + palette), `issues` (palette search badges), `search` and `notifications` (palette results + unread badges). Anything else is optional.
  - Adding a web surface: add declarations to `features/<id>/web.ts`, register the module in `features/registry.ts`, add the entry ids to the matching shell order map, and list the feature's routes/pages/components/locale files in `presets/features/<id>.json` claims.
- **Better Auth UI:** `src/components/auth/` contains locally owned registry components adapted from the base-nova registry; plugin factories/localization adapters live in `src/lib/auth/` and are registered in `routes/__root.tsx`. Prefer these components for authentication, account/security, organization, administrator users, theme, billing and API-key UI. Registry updates must preserve local adapters, translations, organization write locks and cache policies; do not overwrite the directory blindly.
  - Keep the feature-data architecture checks strict for registry components too: app requests, raw mutations and cache changes belong in the owning `features/<feature>/data.ts`; components may consume library hooks and feature hooks. Admin mutations wrap upstream options in `features/admin/data.ts` and also refresh app statistics.
  - Email OTP uses the registry adapter in `src/lib/auth/email-otp-plugin.ts`: `src/components/auth/email-otp/` renders the `/email-otp` view and the sign-in toggle button, and consumes the library's `useSendVerificationOtp`/`useSignInEmailOtp` hooks. Keep `otpLength` and `disableSignUp` in sync with the server `emailOTP` options.
  - Admin users use the Better Auth admin client; search explicitly selects email or name, with filters/sort/pagination in URL state. `AuthPolicyService` plus the auth middleware preserve the restrictions against changing your own role, banning yourself or banning an administrator. Newly introduced upstream destructive actions are not enabled automatically.
  - Billing UI uses `createAppBillingAdapter` in `features/billing/data.ts` against the existing organization billing endpoints, with mock confirmations and role checks. API-key registry UI uses `features/api-keys/data.ts`; the custom key table, one-time secrets, public API authentication and rate limiting remain unchanged. Neither UI migration enables the corresponding Better Auth backend plugin.
- Pages under `src/pages/` map to routes; cross-feature components and layouts live in `src/components/`. Business components live in `src/features/<feature>/components/`; a view may compose components/data from several domains (e.g. an issue's comments and attachments). Extract independent dialogs and sections even when only one page uses them. Admin pages under `_auth/admin/*`; Scalar API docs at `_auth/api-docs`.
- Add shadcn components from repo root: `bunx shadcn@latest add <name> -c apps/web` — files land in `packages/ui/src/components` (per `apps/web/components.json` aliases). Import as `@workspace/ui/components/<name>`.
- **shadcn first (mandatory):** compose UI from `@workspace/ui/components/*`; never hand-roll a primitive that already exists.
  - Raw `<button>`/`<input>`/`<select>`/`<textarea>` with copied classes → `Button`/`Input`/`Select`/`Textarea`. Pills/tags/status → `Badge` (override colors via `variant`/`className`, never copy `badgeVariants` into a `<span>`).
  - Inline errors and banners → `Alert` (`variant="destructive"`); empty/not-found states → `Empty*`; loading placeholders → `Skeleton`, activity indicators → `Spinner` (never `Loader2 + animate-spin`); error copy uses `text-destructive`, not `text-red-500`.
  - Forms → `Field`/`FieldLabel`/`FieldError` (+ `FieldSet`/`FieldLegend`); inputs with icons, suffixes or inline buttons → `InputGroup`; no ad-hoc `div > Label > Input > p-error` blocks.
  - List rows → `Item*`; tables → `Table*`; segmented controls and settings nav → `Tabs`; overlays → `Dialog`/`AlertDialog`/`Sheet`; menus → `DropdownMenu`/`Command`.
  - If a primitive is missing (pagination, sidebar, breadcrumb, kbd, button-group, toggle-group, scroll-area), add it with `bunx shadcn@latest add <name> -c apps/web` instead of writing an equivalent. Keep custom UI only for behavior shadcn does not cover (theme provider, drag & drop, markdown rendering, brand logo) and say why.
  - Extract shared wrappers (e.g. `ConfirmDialog`, `MutationError`, `MarkdownEditor`) instead of copy-pasting the same composition across features. Better Auth UI components keep their structure and adapters but follow the same primitive rules internally.
- `@/*` maps to `apps/web/src/*`.
- **i18n (react-i18next): never hardcode user-facing strings.** All UI text must be referenced via `useTranslation()` → `t("key")`. Translations are split by namespace under `apps/web/src/i18n/locales/{en,zh}/<namespace>.ts` (file name = top-level key, e.g. `en/issues.ts`); `locales/en.ts` and `locales/zh.ts` are the aggregators (`en.ts` stays the single type source via `typeof en`, and every `zh/<ns>.ts` is typed as `typeof en.<ns>` so keys can't drift). A feature owns its namespace files (`features/<id>/web.ts` → `i18nNamespaces`); the scaffold deletes them with the feature and rewrites the aggregators, so a stale `t("deleted.key")` fails typecheck. To change language programmatically use `changeLanguage()` from `@/i18n` (persists to localStorage + updates `<html lang>`). Exception: brand names (e.g. "React Hono Template") and enum values echoed from the API (e.g. `admin`/`user` role codes).
- **Theming:** custom ThemeProvider in `src/components/theme-provider.tsx` (class-based dark mode, `dark/light/system`, localStorage key `theme`). Use `useTheme()` for programmatic changes; the `<html>` class is pre-applied by an inline script in `index.html` to avoid FOUC — keep that script in sync with the provider's storage key if it changes. Tailwind dark variant is `@custom-variant dark (&:is(.dark *))` in `packages/ui/src/styles/globals.css`.
  - **Theme swap workflow:** `packages/ui/src/styles/globals.css` is the structural Tailwind entry (framework/registry imports, `@source` globs, base layer) — never edit it. Swap themes by pasting the raw tweakcn export over `packages/ui/src/styles/theme.css`, keeping its own first line `@import "tailwindcss";` (the compiler dedupes it; removing it breaks `@apply` in globals.css). After any swap, run a production build and grep the emitted CSS for `data-checked`/`no-scrollbar` to confirm nothing regressed, then commit so lint-staged normalizes formatting.

## Style

- Biome enforces: tabs, double quotes, organized imports. Run `bun run format` before committing; the pre-commit hook auto-fixes staged files.

## Deploy

Push to `main` auto-deploys via GitHub Actions (needs repo secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`):

- `ci.yml` — runs on every pull request and on pushes to `main`; also exposes `workflow_call`. Its `quality` job (`bun install --frozen-lockfile` → `bun run check` → `bun run typecheck` → `bun run build` → `bun run test`) is reused by every deployment workflow, whose deploy jobs require `needs: quality`. The test step enables the PostgreSQL/Redis smoke test against temporary service containers. All workflows read Bun from `package.json` via `bun-version-file`.
- `deploy-api.yml` — triggers on `apps/api/**`, `packages/shared/**`, `bun.lock`, root `package.json`, `tsconfig.base.json`, or workflow changes; deploys source directly (wrangler bundles Hono, no build step). Shares a concurrency group with `configure-ai.yml`: an active run is not cancelled, but only one pending run is retained.
- `deploy-web.yml` — triggers on `apps/web/**`, `packages/ui/**`, `packages/shared/**`, `apps/api/**` (web's `tsc -b` type-checks api source via the `@api/*` alias), `bun.lock`, root `package.json`, `tsconfig.base.json`, or workflow changes; builds with `VITE_API_URL=https://react-hono-api.poco-ai.workers.dev`, then deploys.
- `configure-ai.yml` — manual workflow that applies remote D1 migrations, sets the AI provider secret and deploys the API. It calls the CI `quality` job first, so migrations never run on unchecked code.

Manual: `bun run deploy` inside the app dir; build Web with `VITE_API_URL` first for cross-origin hosting. For a new deployment, follow `docs/部署.md` to update the public API/Web URLs and `TRUSTED_ORIGINS` together.
